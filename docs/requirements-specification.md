# Especificación de Requerimientos - API de Citas Médicas y Formulario de Autoatención

## 1. Alcance y contexto

Este documento define los requerimientos funcionales y no funcionales del sistema **MediCitas Anglo**, enfocados en la **API de citas médicas** y su interacción con el **formulario web de autoatención para pacientes**. No cubre el cliente de escritorio ni los procesos internos de gestión (Admisión, Médico, Administrador), los cuales corresponden a otra etapa del proyecto.

La Clínica Anglo Americana opera dos sedes en Lima (San Isidro y La Molina), cuenta con más de 80 especialidades y subespecialidades, y atiende alrededor de 250 mil pacientes al año.

## 2. Actores

| Actor | Tipo | Descripción | Interacción principal | Responsabilidad |
|---|---|---|---|---|
| **Paciente** | Persona (entidad externa / usuario final) | Usuario que solicita, consulta o programa citas a través del formulario de autoatención / API web. | Consulta de disponibilidad de especialidades, reserva de cupos y recepción de notificaciones de confirmación. | Brindar información correcta de su identidad y seguro, y confirmar su asistencia a la cita. |
| **Servicio de Mensajería Externalizado** | Sistema externo | API externa para el envío de SMS/Email automáticos. | Envío de recordatorios y confirmaciones programadas a los pacientes. | Garantizar la entrega de las notificaciones para reducir el ausentismo. |

## 3. Requerimientos Funcionales (RF)

| Código | Nombre | Descripción | Prioridad | Criterio de Verificación |
|---|---|---|---|---|
| **RF-01** | Registro de paciente | El formulario debe permitir que un paciente nuevo se registre en el sistema, validando la unicidad de su número de documento de identidad antes de crear el perfil, en cumplimiento de la responsabilidad del actor Paciente de brindar información correcta de su identidad. | Alta | Intentar registrar a un paciente con un número de documento ya existente; la API debe rechazar la solicitud y el formulario debe mostrar un mensaje de error claro. |
| **RF-02** | Identificación del paciente | El formulario debe permitir identificar a un paciente ya registrado mediante su número de documento, para retomar su perfil sin duplicar el registro. | Alta | Ingresar el número de documento de un paciente existente y verificar que el formulario recupere su perfil en vez de crear uno nuevo. |
| **RF-03** | Asociación de aseguradora | El paciente debe poder indicar en el formulario su aseguradora de salud (por ejemplo, Rímac, Pacífico, La Positiva o Mapfre, con las que la clínica mantiene convenio) y su tipo de plan, quedando dicha información asociada a su perfil. | Media | Completar el campo de seguro en el formulario, enviar la solicitud y verificar que la API almacene correctamente el dato en el perfil del paciente. |
| **RF-04** | Consulta de especialidades disponibles | La API debe exponer un listado de las especialidades médicas activas (dentro de las más de 80 que ofrece la clínica en sus sedes de San Isidro y La Molina) para que el formulario las presente al paciente como punto de partida de la búsqueda. | Alta | Consultar el endpoint de especialidades y verificar que la respuesta coincida con las especialidades configuradas como activas por sede. |
| **RF-05** | Consulta de disponibilidad de citas | La API debe permitir consultar, para una especialidad, sede y rango de fechas determinado, los cupos disponibles de los médicos correspondientes. | Alta | Solicitar la disponibilidad de una especialidad con cupos conocidos y verificar que la respuesta refleje exactamente los horarios libres. |
| **RF-06** | Reserva de cita mediante formulario | El paciente debe poder reservar un cupo disponible desde el formulario, generando una cita asociada a su perfil, al médico, fecha, hora y motivo de consulta. | Alta | Completar el flujo de reserva desde el formulario y verificar que la cita quede registrada correctamente a través de la API. |
| **RF-07** | Bloqueo de cupos concurrentes | La API debe rechazar la reserva de un cupo si este ya fue tomado por otra solicitud procesada de forma simultánea, evitando el doble agendamiento identificado como problema operativo recurrente. | Alta | Enviar dos solicitudes de reserva simultáneas para el mismo cupo desde el formulario o mediante pruebas de API; solo una debe ser aceptada. |
| **RF-08** | Prevención de citas duplicadas en el mismo horario | La API debe impedir que un paciente reserve una nueva cita en un horario donde ya cuenta con una cita activa. | Alta | Intentar reservar una cita para un paciente en un horario idéntico a una cita previa ya confirmada; la API debe rechazar la solicitud. |
| **RF-09** | Reprogramación de cita por el paciente | El paciente debe poder, desde el formulario, trasladar una cita propia a una nueva fecha u hora disponible, liberando el cupo original. | Media | Reprogramar una cita desde el formulario y verificar que el cupo original quede disponible nuevamente y el nuevo quede ocupado. |
| **RF-10** | Anulación de cita por el paciente | El paciente debe poder cancelar una cita propia que se encuentre en estado pendiente, mediante el formulario, cumpliendo con su responsabilidad de confirmar o desistir oportunamente de su asistencia. | Media | Cancelar una cita pendiente desde el formulario y verificar que su estado cambie y el cupo quede liberado en la API. |
| **RF-11** | Confirmación automática de reserva | Al completarse una reserva, la API debe generar una notificación de confirmación dirigida al paciente a través del Servicio de Mensajería Externalizado, cumpliendo la interacción principal descrita para el actor Paciente ("recepción de notificaciones de confirmación"). | Alta | Reservar una cita y verificar que se genere una solicitud de envío hacia el servicio de mensajería con los datos correctos de la cita. |
| **RF-12** | Recordatorios automáticos previos a la cita | La API debe programar el envío de un recordatorio automático al paciente antes de la fecha y hora de su cita confirmada, en línea con la responsabilidad del Servicio de Mensajería Externalizado de garantizar la entrega de notificaciones para reducir el ausentismo. | Media | Revisar la cola o tabla de notificaciones programadas y verificar que exista un recordatorio asociado con el horario de envío correcto. |
| **RF-13** | Trazabilidad del estado de notificaciones | La API debe registrar el estado de cada notificación enviada al Servicio de Mensajería Externalizado (enviado, fallido, pendiente). | Baja | Consultar el registro de notificaciones de una cita y validar que el estado coincida con la respuesta real del servicio de mensajería externo. |
| **RF-14** | Manejo de fallos del servicio de mensajería | Si el Servicio de Mensajería Externalizado no responde o falla, la API debe registrar el error sin afectar el estado de la cita ya confirmada, dado que se trata de una dependencia de un proveedor externo. | Media | Simular la caída del servicio de mensajería al confirmar una cita y verificar que la cita permanezca confirmada mientras el error queda registrado. |

## 4. Requerimientos No Funcionales (RNF)

Clasificados según ISO/IEC 25010.

| Código | Característica | Nombre | Descripción | Prioridad | Criterio de Verificación |
|---|---|---|---|---|---|
| **RNF-01** | Seguridad | Protección de datos personales y de salud | Toda comunicación entre el formulario y la API debe realizarse mediante HTTPS, y los datos sensibles de salud del paciente. | Alta | Verificar que las peticiones al API solo se acepten sobre HTTPS y que los datos clínicos no sean accesibles sin la identificación correspondiente del paciente. |
| **RNF-02** | Seguridad | Validación y saneamiento de entradas | La API debe validar y sanear todos los datos recibidos desde el formulario para prevenir inyección SQL, XSS u otros ataques comunes en formularios públicos. | Alta | Enviar entradas maliciosas conocidas (payloads de SQLi/XSS) a los endpoints del formulario y verificar que sean rechazadas o neutralizadas sin afectar la base de datos. |
| **RNF-03** | Seguridad | Control de solicitudes abusivas | La API debe limitar la cantidad de solicitudes por paciente/IP en un periodo determinado (rate limiting) para prevenir abuso del formulario público. | Media | Enviar un número elevado de solicitudes en un corto periodo desde el mismo origen y verificar que la API comience a rechazarlas o retrasarlas. |
| **RNF-04** | Rendimiento | Latencia de consulta de disponibilidad | Las peticiones al endpoint de disponibilidad de especialidades y médicos no deben exceder los 3 segundos de respuesta. | Alta | Medir el tiempo de respuesta del endpoint de disponibilidad bajo condiciones de red estándar mediante una herramienta como Postman o JMeter. |
| **RNF-05** | Disponibilidad | Disponibilidad del formulario | El formulario web y la API deben mantener una disponibilidad mínima del 99% en horario de atención, permitiendo su uso continuo por los pacientes de ambas sedes. | Alta | Monitorear el tiempo de actividad del servicio durante un periodo de prueba y calcular el porcentaje de disponibilidad efectivo. |
| **RNF-06** | Usabilidad | Claridad de mensajes al paciente | Los errores de validación y las excepciones del sistema deben mostrarse al paciente mediante mensajes claros en español, sin exponer detalles técnicos (stacktrace, códigos SQL). | Alta | Provocar un error de validación o de conexión y verificar que el formulario muestre un mensaje comprensible sin información técnica. |
| **RNF-07** | Fiabilidad | Consistencia ante fallos de conexión | Si la conexión entre el formulario y la API se interrumpe durante una reserva, el sistema no debe generar citas duplicadas ni cupos inconsistentes al reintentar. | Media | Interrumpir la conexión durante el envío de una reserva y verificar, al reintentar, que no se generen registros duplicados ni cupos bloqueados erróneamente. |
| **RNF-8** | Mantenibilidad | Documentación de la API | Los endpoints de la API destinados al formulario de pacientes deben estar documentados (por ejemplo, mediante OpenAPI/Swagger), incluyendo parámetros, respuestas y códigos de error. | Baja | Revisar la documentación publicada de la API y contrastarla con el comportamiento real de al menos tres endpoints. |
